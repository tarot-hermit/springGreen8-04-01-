# SpringGreen8 발표 대본

권장 발표 시간: 약 15-20분  
발표 톤: 포트폴리오 면접/프로젝트 시연용, 차분하지만 구현 근거가 드러나는 방식

## 1. Cover

안녕하세요. Spring MVC 기반 콘텐츠 커뮤니티 웹 서비스, SpringGreen8을 개발한 이태경입니다.

SpringGreen8은 영화, 드라마, 애니메이션 정보를 한 곳에서 탐색하고, 상세 정보 확인, 예고편 재생, 리뷰와 댓글 작성, 찜과 봤어요 기록, 그리고 관리자 운영까지 이어지도록 만든 통합 웹 서비스입니다.

기술적으로는 Java 11, Spring MVC 4.3, MyBatis, MySQL을 중심으로 구성했고, TMDB API와 YouTube API를 활용해 콘텐츠 데이터와 예고편 데이터를 연동했습니다. 이번 발표에서는 프로젝트의 배경, 구조, 핵심 기능, 그리고 최근 수정으로 보강한 부분까지 순서대로 설명드리겠습니다.

## 2. Contents

발표 순서는 총 일곱 가지입니다.

먼저 개발 배경과 문제 정의, 프로젝트 목표를 설명하고, 이어서 기술 스택과 전체 시스템 구조를 말씀드리겠습니다. 그다음 15개 DB 테이블 구조와 핵심 기능인 탐색, 검색, 상세 페이지를 살펴보겠습니다.

이 프로젝트에서 특히 신경 쓴 예고편 fallback 알고리즘도 별도로 설명드리고, 이후 사용자 기능, 커뮤니티 기능, 관리자 기능을 실행 화면과 함께 보여드리겠습니다. 마지막으로 개선 사례, 성과, 한계와 향후 계획을 정리하겠습니다.

그래서 발표를 들으실 때는 먼저 전체 프로젝트의 큰 흐름을 이해하고, 이어지는 최신 수정 장표에서 어떤 부분이 보강되었는지 확인해주시면 좋겠습니다.

## 4. 개발 배경

이 프로젝트의 출발점은 콘텐츠 탐색 경험이 여러 플랫폼에 흩어져 있다는 문제였습니다.

영화, 드라마, 애니메이션 정보는 각각 다른 서비스나 페이지에 분산되어 있고, 사용자는 콘텐츠를 비교하거나 이어서 탐색하기가 어렵습니다. 또 대부분의 검색은 제목 중심이라서 키워드나 태그 기반으로 새로운 콘텐츠를 발견하기 어렵고, 오타나 띄어쓰기 차이에도 취약합니다.

마지막으로 콘텐츠를 확인한 뒤 예고편, 리뷰, OTT 제공처, 개인 기록까지 이어지는 과정이 분리되어 있어 사용자의 반응이 한 서비스 안에서 자연스럽게 쌓이지 않는다고 판단했습니다.

## 5. 문제 정의와 목표

제가 정의한 핵심 문제는 사용자가 원하는 것이 단순 검색이 아니라, 콘텐츠를 발견하고 소비하고 반응하는 전체 흐름이라는 점입니다.

그래서 SpringGreen8의 목표는 영화, 드라마, 애니메이션을 통합해서 탐색할 수 있는 환경을 만들고, 제목 검색뿐 아니라 키워드, 해시태그, 오타 보정까지 포함한 검색 UX를 제공하는 것이었습니다.

또 상세 페이지에서는 예고편, 출연진, OTT 제공처, 키워드를 함께 제공하고, 리뷰, 댓글, 찜, 컬렉션 같은 반응 기능까지 연결했습니다. 운영자 관점에서는 관리자 대시보드, 신고 처리, 통계 기능을 포함해 실제 서비스 운영 흐름도 고려했습니다.

## 6. 서비스 흐름

사용자 흐름은 홈 탐색, 검색, 상세 확인, 반응, 기록으로 이어집니다.

비로그인 사용자는 콘텐츠 탐색과 검색, 상세 조회까지 사용할 수 있고, 로그인 사용자는 리뷰 작성, 댓글, 좋아요, 찜, 봤어요, 컬렉션 기능까지 사용할 수 있습니다.

관리자는 별도 관리자 페이지에서 회원, 리뷰, 신고, 통계 데이터를 확인하고 처리할 수 있습니다. 즉 사용자 입장에서는 콘텐츠 소비 흐름이 끊기지 않고, 관리자 입장에서는 운영에 필요한 데이터를 한 곳에서 다룰 수 있도록 설계했습니다.

## 7. 기술 스택

기술 스택은 전통적인 Spring MVC 구조를 기반으로 구성했습니다.

백엔드는 Java 11, Spring MVC 4.3, Spring AOP, Interceptor를 사용했고, 서버는 Tomcat 9 환경입니다. 프론트엔드는 JSP, JSTL, Bootstrap, jQuery와 Vanilla JavaScript를 사용했습니다.

데이터베이스는 MySQL 8과 MyBatis Mapper XML로 연동했고, 외부 API는 TMDB API와 YouTube Data API를 사용했습니다. 사용자 인증과 보안 쪽에서는 세션 기반 로그인, XSS 필터, 입력 검증, 관리자 인터셉터를 적용했습니다. 이메일 인증은 JavaMailSender와 Gmail SMTP를 이용해 6자리 인증 코드를 발송하는 방식으로 구현했습니다.

## 8. 전체 시스템 구조

전체 구조는 Browser에서 들어온 요청이 DispatcherServlet을 거쳐 Controller, Service, DAO, MyBatis Mapper, MySQL로 이어지는 전형적인 Spring MVC 계층 구조입니다.

Controller는 요청 파라미터 검증과 뷰 바인딩에 집중하고, Service는 비즈니스 로직, 외부 API 호출, 캐시 처리를 담당합니다. DAO와 Mapper는 SQL 관리와 데이터 접근을 맡습니다.

공통 기능으로는 인기 검색어와 통계 데이터를 공통 주입하는 GlobalViewOptionsAdvice, 모든 요청을 감싸는 XssFilter와 XssRequestWrapper, 관리자 권한을 확인하는 AdminInterceptor, 로그인 세션 만료와 재인증을 다루는 LoginSessionInterceptor를 구성했습니다.

## 9. Controller 책임 분리

Controller는 기능군별로 분리했습니다.

MovieController는 콘텐츠 목록, 검색, 상세, 찜과 봤어요를 담당하고, UserController는 회원가입, 로그인, 프로필, 비밀번호 변경, 이메일 인증을 담당합니다.

ReviewController와 CommentController는 커뮤니티 기능을 맡고, CollectionController는 사용자 컬렉션을 담당합니다. AdminController는 대시보드와 회원, 리뷰, 신고, 통계를 처리하고, ReportController는 신고 접수, NotificationController는 알림 조회와 읽음 처리를 담당합니다.

이렇게 나눈 이유는 기능이 많아질수록 Controller 단위의 책임을 명확히 해야 유지보수하기 쉽기 때문입니다.

## 10. DB 전체 테이블 구조

DB는 총 15개 테이블로 구성했습니다.

계정과 콘텐츠 영역에는 users, movie, genre, movie_genre가 있고, 커뮤니티 영역에는 review, review_like, comment가 있습니다. 개인 기록 영역에는 watchlist, watched, collection, collection_movie가 있습니다.

운영과 알림 영역에는 report, notification, search_history가 있고, 예고편 캐시를 위해 media_video_cache 테이블을 별도로 두었습니다. 전체적으로 사용자, 콘텐츠, 커뮤니티, 개인 기록, 운영이라는 다섯 개 도메인으로 나눠 설계했습니다.

## 11. users와 movie 테이블

핵심 테이블 중 먼저 users와 movie입니다.

users 테이블은 회원 계정과 프로필 정보를 저장합니다. user_id는 중복을 막기 위해 UNIQUE로 설정했고, 비밀번호는 해시 값으로 저장합니다. 사용자 역할은 USER와 ADMIN으로 나눠 권한 처리에 활용했습니다.

movie 테이블은 TMDB에서 가져온 콘텐츠를 로컬에 저장하는 테이블입니다. tmdb_id를 UNIQUE로 두어 같은 콘텐츠가 중복 저장되지 않도록 했고, 제목, 원제, 줄거리, 포스터, 배경 이미지, 개봉일, 러닝타임, 평점, 인기도 같은 데이터를 저장합니다.

## 12. 장르와 예고편 캐시 테이블

genre 테이블은 TMDB 장르 목록을 로컬에 동기화하기 위한 마스터 테이블이고, movie_genre는 영화와 장르 사이의 N:N 관계를 표현합니다.

media_video_cache 테이블은 예고편 처리에서 중요한 역할을 합니다. 콘텐츠 타입, TMDB ID, 시즌 번호, 영상 키를 기준으로 캐시를 저장해둡니다. 이미 성공한 예고편이 있으면 외부 API를 다시 호출하지 않고 캐시를 사용하도록 해서 응답 안정성과 API 사용량을 모두 고려했습니다.

## 13. 커뮤니티 테이블

커뮤니티 기능은 review, comment, review_like로 구성됩니다.

review 테이블은 리뷰 본문, 별점, 스포일러 여부, 좋아요 수 캐시를 저장합니다. comment 테이블은 리뷰에 달리는 댓글을 저장하고, 댓글 작성 시 리뷰 작성자에게 알림이 생성되도록 연결했습니다.

review_like는 사용자와 리뷰 번호를 복합 키로 사용해 좋아요 중복을 막았습니다. 좋아요는 INSERT와 DELETE 방식으로 토글하고, 토글 이후 review 테이블의 like_cnt를 재계산합니다. 본인 리뷰에는 좋아요를 누를 수 없도록 제한했습니다.

## 14. 개인 기록 테이블

개인 기록 기능은 watchlist, watched, collection, collection_movie로 구성했습니다.

watchlist는 찜 목록을 저장하고, watched는 사용자가 봤다고 표시한 콘텐츠를 저장합니다. 두 기능 모두 TMDB ID를 로컬 movie_no로 변환한 뒤 저장하도록 해서 콘텐츠 데이터의 기준을 맞췄습니다.

collection은 사용자가 직접 만드는 컬렉션이고, collection_movie는 컬렉션과 콘텐츠의 N:N 관계를 표현합니다. 컬렉션은 공개/비공개 상태를 가질 수 있고, 비공개 컬렉션은 소유자만 접근할 수 있도록 처리했습니다.

## 15. 운영, 알림, 검색 기록 테이블

운영 영역에는 report, notification, search_history가 있습니다.

report는 신고 내역을 저장합니다. 신고가 PROCESSED 상태가 되면 대상 리뷰를 블라인드 처리하도록 서비스 로직과 연결했습니다. notification은 댓글, 좋아요, 신고 처리 결과 같은 사용자 알림을 저장합니다.

search_history는 검색어와 검색 결과 수, 검색 시각을 저장합니다. 첫 페이지 검색만 기록하고, 같은 키워드는 삭제 후 다시 저장하는 방식으로 최근 검색어 중복 적재를 방지했습니다.

## 16. DB 트랜잭션 흐름

이 프로젝트에서는 외부 API의 TMDB ID와 로컬 DB의 movie_no를 연결하는 흐름이 중요했습니다.

리뷰, 댓글, 좋아요, 찜, 봤어요, 컬렉션 기능은 모두 콘텐츠를 기준으로 동작하기 때문에, 먼저 TMDB ID로 로컬 movie를 조회하고 없으면 저장한 뒤 movie_no를 연결합니다.

리뷰 수정과 삭제는 작성자 또는 관리자 권한을 확인하고, 좋아요는 토글 후 like_cnt를 재계산합니다. 댓글 작성 시에는 리뷰 작성자에게 알림이 생성되고, 관리자 신고 처리는 상태 변경과 블라인드 처리를 하나의 트랜잭션 흐름으로 묶었습니다.

## 17. 핵심 기능 1: 콘텐츠 탐색

첫 번째 핵심 기능은 콘텐츠 탐색입니다.

홈 화면에서는 인기 콘텐츠, 주간 트렌딩, 현재 상영작, 개봉 예정작을 확인할 수 있습니다. 기본적으로 TMDB 데이터를 활용하되, 장르별 접근과 미디어 타입 분리 탭을 제공해 영화, 드라마, 애니메이션을 나눠 탐색할 수 있도록 했습니다.

정렬은 인기순, 평점순, 방영순을 제공해서 사용자가 원하는 기준으로 콘텐츠를 비교할 수 있게 했습니다.

## 18. 실행 화면: Discovery

여기서는 실제 홈 화면을 보여드립니다.

상단에는 Hero 배너가 있고, 아래로 인기 콘텐츠와 탐색 섹션이 이어집니다. 발표에서는 이 화면을 통해 앞에서 설명한 탐색 기능이 실제 브라우저에서 어떻게 보이는지 확인할 수 있습니다.

단순히 API 데이터를 나열하는 것이 아니라, 사용자가 자연스럽게 콘텐츠를 클릭하고 상세 페이지로 이동할 수 있도록 섹션 구조를 구성했습니다.

## 19. 핵심 기능 2: 검색

두 번째 핵심 기능은 검색입니다.

검색은 제목 검색, 키워드 검색, 해시태그 검색, 최근 검색어, 인기 검색어까지 다섯 가지 흐름을 통합했습니다. 예를 들어 사용자가 `#로맨스`처럼 입력하면 단순 제목 검색이 아니라 키워드 기반 탐색으로 이어지도록 처리했습니다.

최근 검색어는 사용자 편의를 위해 저장하고, 인기 검색어는 전체 사용자 검색 기록을 집계해 보여줍니다. 이를 통해 사용자는 본인이 찾던 콘텐츠뿐 아니라 다른 사용자가 많이 찾는 콘텐츠도 발견할 수 있습니다.

## 20. 검색 fallback 알고리즘

검색은 한 번의 API 호출로 끝내지 않고 단계별 fallback을 적용했습니다.

먼저 입력 검색어로 제목 검색을 수행하고, 결과 품질이 낮으면 보정된 제목으로 다시 검색합니다. 해시태그나 키워드 입력인 경우 TMDB keyword 검색을 수행하고, 키워드 ID를 기반으로 discover API를 조합합니다.

마지막에는 여러 단계에서 얻은 결과를 통합하고 중복을 제거합니다. 특히 `#` 문자가 URL fragment로 처리되는 문제를 막기 위해 클라이언트에서 encodeURIComponent를 적용했고, 서버에서도 decode 처리를 보강했습니다.

## 21. 핵심 기능 3: 상세 페이지

상세 페이지는 이 서비스의 중심 화면입니다.

한 화면에서 줄거리, 개봉 정보, 예고편, 출연진, 키워드 태그, OTT 제공처, 리뷰를 모두 확인할 수 있습니다. 키워드 태그를 클릭하면 다시 키워드 검색으로 이어지도록 연결했습니다.

드라마 콘텐츠의 경우 시즌 예고편이 없을 수 있어서, 시즌별 예고편을 먼저 찾고 없으면 시즌 1, 그래도 없으면 시리즈 전체 예고편으로 fallback하는 구조를 적용했습니다.

## 22. 실행 화면: 검색과 상세

여기서는 검색 결과와 상세 페이지 실행 화면을 보여드립니다.

검색 결과 화면에서는 최근 검색어와 결과 카드가 함께 보이고, 로그인 상태에서는 검색 기록이 사용자 흐름에 맞게 저장됩니다. 상세 페이지에서는 콘텐츠 메타데이터, 리뷰 입력 영역, 키워드, 예고편 영역을 확인할 수 있습니다.

이 장표는 앞에서 설명한 검색과 상세 기능이 실제 사용자 흐름 안에서 어떻게 이어지는지 보여주는 부분입니다.

## 23. 예고편 처리 전체 흐름

이 프로젝트에서 가장 많이 신경 쓴 부분 중 하나가 예고편 처리입니다.

예고편은 TMDB ko-KR 결과를 먼저 확인하고, 없으면 en-US 결과를 확인합니다. 그래도 없으면 로컬 캐시를 확인하고, 캐시에도 없으면 YouTube 검색으로 넘어갑니다.

YouTube 후보는 필터링과 점수화를 거치고, 실제로 embed 재생이 가능한지 검증한 뒤 캐시에 저장합니다. 이렇게 8단계 fallback을 둔 이유는 외부 API 응답이 항상 안정적이지 않기 때문에, 사용자가 상세 페이지에서 최대한 빈 예고편 영역을 보지 않게 하기 위해서입니다.

## 24. 예고편 후보 필터링과 점수화

YouTube 검색 결과는 그대로 사용하지 않았습니다.

쇼츠, 리액션, 리뷰, OST, 오프닝, 엔딩, 클립, 해설 영상처럼 예고편으로 보기 어려운 후보는 제외했습니다. 그다음 콘텐츠명과 제목 일치 여부, 공식 채널과의 유사도, official, trailer, teaser 같은 키워드 포함 여부를 기준으로 점수를 매겼습니다.

드라마는 시즌 정보까지 고려해 시즌별 전용 예고편을 우선 찾고, 없으면 시즌 1과 시리즈 전체로 fallback했습니다. 최종적으로는 embeddable 여부, 공개 상태, 업로드 처리 상태, 한국 지역 재생 가능 여부를 검증한 후보만 캐시에 저장했습니다.

## 25. 회원가입, 로그인, 이메일 인증

사용자 계정 기능은 회원가입, 로그인, 이메일 인증, 세션 관리까지 포함했습니다.

회원가입에서는 아이디, 비밀번호, 이메일, 닉네임을 검증하고 중복 확인을 수행합니다. 이메일 인증은 6자리 코드를 Gmail SMTP로 발송하고, 사용자가 일정 시간 안에 입력하도록 구성했습니다.

로그인은 실패 횟수를 세션에 기록해 5회 실패 시 10분 동안 잠금 처리하고, 로그인 성공 시 기존 세션을 무효화한 뒤 새 세션을 발급합니다. 또한 카카오 로그인은 KakaoLoginService를 통해 토큰 교환과 프로필 연동을 처리했습니다.

## 26. 최신 수정: 인증 흐름 보강

최근 수정에서는 회원과 인증 구간에 사용자 진입 경로와 보호 장치를 추가했습니다.

카카오 로그인은 인가 코드를 받은 뒤 프로필을 조회하고, 기존 계정과 연결할지 신규 가입으로 처리할지 분기하도록 구성했습니다.

이메일 인증은 코드 발송 시각을 세션에 저장하고, 서버에서 5분 만료 여부를 검증하도록 보강했습니다. 로그인 보호도 강화해서 5회 실패 시 10분 잠금, 동일 계정 중복 세션 정리, 탈퇴나 비밀번호 변경 시 활성 세션 종료까지 반영했습니다.

## 27. 실행 화면: Account

여기서는 로그인 화면과 마이페이지 실행 화면을 확인할 수 있습니다.

로그인 화면에는 일반 로그인과 카카오 로그인 진입점이 함께 제공됩니다. 마이페이지에서는 프로필 영역과 개인 활동 대시보드를 통해 사용자의 리뷰, 댓글, 찜, 컬렉션 같은 활동을 한 곳에서 확인할 수 있습니다.

이 화면은 계정 기능이 단순 로그인에서 끝나는 것이 아니라, 사용자 활동 관리로 이어진다는 점을 보여줍니다.

## 28. 리뷰, 댓글, 개인 기록

리뷰와 기록 기능은 콘텐츠 소비 이후의 사용자 반응을 서비스 안에 남기기 위한 기능입니다.

리뷰는 TMDB ID를 movie_no로 변환한 뒤 저장하고, 사용자는 별점과 리뷰를 작성할 수 있습니다. 댓글 작성 시에는 리뷰 작성자에게 알림이 자동 생성되고, 본인 리뷰에는 좋아요를 누를 수 없게 했습니다.

개인 기록 쪽에서는 찜, 봤어요, 컬렉션 기능을 제공했습니다. 컬렉션은 제목과 설명 길이를 검증하고, 공개와 비공개 상태를 지원합니다. 비공개 컬렉션은 소유자만 접근할 수 있도록 권한을 확인했습니다.

## 29. 최신 수정: 커뮤니티 구조 보강

최근 수정에서는 커뮤니티 기능에 2-depth 댓글 구조와 알림 서비스 계층을 추가했습니다.

comment 테이블에 parent_id를 추가하고, CommentVO에는 parentId와 parentUserName을 추가했습니다. 이를 통해 댓글에 대한 답글 구조를 만들고, 상세 페이지에서는 답글 입력창, 들여쓰기, 부모 작성자 표시를 함께 렌더링했습니다.

또 알림 흐름도 정리했습니다. 댓글, 좋아요, 신고 결과 같은 이벤트는 NotificationService가 생성하고, NotificationController는 조회와 읽음 처리에 집중하도록 역할을 분리했습니다.

## 30. 관리자 기능과 보안

관리자 기능은 사용자 서비스와 분리된 운영 영역입니다.

관리자 대시보드에서는 회원 수, 금일 리뷰, 미처리 신고, 대기 댓글 같은 요약 데이터를 확인할 수 있습니다. 신고 처리는 PROCESSED 상태로 전환될 때 리뷰 블라인드 처리를 트랜잭션으로 수행합니다.

보안 측면에서는 /admin/** 경로에 AdminInterceptor를 적용해 권한을 일괄 확인하고, InputValidator로 회원, 리뷰, 댓글, 신고 입력값을 공통 검증했습니다. XssFilter는 위험 태그와 이벤트를 제거하되, multipart 요청은 제외하도록 범위를 조정했습니다.

## 31. 최신 수정: 관리자 운영 흐름 보강

최근 수정에서는 관리자 액션과 사용자에게 돌아가는 결과를 더 직접적으로 연결했습니다.

신고가 PROCESSED 상태가 되면 리뷰를 블라인드 문구로 전환하고, 상태 변경을 서비스 계층에서 처리하도록 했습니다. 또한 신고 결과는 REPORT 알림으로 신고자에게 전달되도록 NotificationService와 연결했습니다.

회원 운영에서는 권한 변경 시 현재 세션의 loginUser를 갱신하고, 강제 탈퇴 처리 시 활성 세션도 종료되도록 했습니다. 이를 통해 관리자 화면의 조치가 실제 사용자 상태와 일관되게 반영되도록 보강했습니다.

## 32. 실행 화면: Admin

여기서는 관리자 실행 화면입니다.

대시보드에서는 운영 요약 데이터와 빠른 접근 카드가 보이고, 신고 관리 화면에서는 신고 목록과 처리 상태를 확인할 수 있습니다. 발표에서는 이 화면을 통해 관리자 기능이 단순 목록 조회가 아니라, 실제 운영 액션과 연결되어 있다는 점을 보여주면 좋습니다.

특히 신고 처리와 알림, 블라인드 전환이 하나의 흐름으로 이어지는 부분을 강조하겠습니다.

## 33. 입력 검증과 보안 개선

기능 구현 이후에는 입력 검증과 보안 구조도 정리했습니다.

개선 전에는 프론트와 서버 검증 규칙이 중복되거나 불일치하는 문제가 있었고, 비밀번호 변경 시 현재 비밀번호 확인이 부족했습니다. 또한 XSS 필터가 일반 입력까지 과하게 탐지하거나, SQL 예약어가 포함된 정상 검색어까지 차단하는 문제가 있었습니다.

개선 후에는 InputValidator 중심으로 검증 규칙을 통합하고, 비밀번호 변경과 세션 재확인을 추가했습니다. XssFilter와 RequestWrapper는 범위를 최소화했고, 예약어 판단도 정교화해 정상 검색어는 통과하도록 수정했습니다.

## 34. 최신 수정 규모

최근 수정은 화면만 바꾼 것이 아니라 SQL 패치와 Mapper, 서비스 로직까지 함께 변경한 작업이었습니다.

SQL patch 파일에는 댓글 parent_id, login_attempt, withdrawn_user_id, 신고 중복 정리 같은 변경이 포함되어 있습니다. create_missing_tables.sql 기준 핵심 테이블은 13개로 정리했고, git diff 기준으로 122개 파일이 변경되었습니다.

이 장표는 최신 수정이 단순 UI 보정이 아니라 데이터 구조, 인증, 운영 로직까지 함께 조정한 업데이트였다는 점을 보여주기 위한 장표입니다.

## 35. 개선 사례와 문제 해결

프로젝트를 진행하면서 발견한 문제는 원인 분석, 조치, 재발 방지 관점으로 정리했습니다.

첫째, `#` 검색어가 URL fragment로 해석되어 쿼리가 누락되는 문제가 있었고, encodeURIComponent와 서버 decode 처리로 해결했습니다.

둘째, 페이지 이동 시 최근 검색어가 반복 저장되는 문제가 있어 세션 기반 dedup과 같은 키워드 삭제 후 재저장 방식으로 수정했습니다.

셋째, TMDB 한국어 응답에 예고편이 없을 때 상세 페이지가 비는 문제가 있어 ko-KR, en-US, 캐시, YouTube 검색으로 이어지는 fallback 체인을 만들었습니다.

그 외에도 상세 키워드 클릭 연결, 관리자 통계 공통 주입, SQL 예약어 과탐 문제를 각각 라우팅 신설, GlobalViewOptionsAdvice, 예약어 판단 정교화로 개선했습니다.

## 36. 프로젝트 성과

프로젝트 결과를 정리하면, SpringGreen8은 탐색, 검색, 상세, 커뮤니티, 관리자까지 하나의 흐름으로 통합한 웹 서비스입니다.

DB는 15개 테이블로 구성했고, 기능군별 Controller를 10개 이상 분리했습니다. 예고편은 8단계 fallback 체인을 구축했고, 검색은 제목, 키워드, 해시태그, fallback, 통합 결과 처리까지 다섯 가지 흐름을 지원합니다.

성과 측면에서는 탐색에서 검색, 상세, 반응, 기록, 운영까지 이어지는 사용자 경험을 만들었고, XssFilter, InputValidator, AdminInterceptor를 통해 입력과 권한 방어도 함께 고려했습니다.

## 37. 한계와 향후 개선 방향

남은 한계도 있습니다.

가장 큰 한계는 통합 테스트와 자동화 테스트가 부족하다는 점입니다. 또한 현재는 로컬 수동 배포에 의존하고 있어 CI/CD 구성이 필요합니다. 개인화 추천도 리뷰와 찜 데이터를 더 활용해 고도화할 수 있고, 모바일과 태블릿 사용성도 추가 보완이 필요합니다.

향후에는 먼저 JUnit 기반 서비스 레이어 테스트와 CI 파이프라인, 로깅과 모니터링을 구성하고 싶습니다. 다음 단계로는 리뷰와 찜 기반 개인 추천, 유사 콘텐츠 추천, 별점 기반 큐레이션을 확장하고, 마지막으로 반응형 UI 전면 개선과 배포 자동화, 캐시 및 API 호출 최적화를 진행할 계획입니다.

## 38. Closing

마무리하겠습니다.

SpringGreen8은 단순히 기능을 많이 붙인 프로젝트라기보다, 사용자가 콘텐츠를 발견하고, 확인하고, 반응하고, 기록하는 서비스 경험을 하나의 흐름으로 설계해본 프로젝트입니다.

Spring MVC 기반 구조 위에서 15개 DB 테이블, 10개 이상의 Controller, 8단계 예고편 fallback, 검색과 커뮤니티, 관리자 기능까지 구현하면서 웹 서비스의 전체적인 흐름을 경험할 수 있었습니다.

이상으로 발표를 마치겠습니다. 감사합니다.
